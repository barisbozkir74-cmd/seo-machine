For each of the 10 tables (projects, stages, rules, competitors, keywords, keyword_clusters, pages, internal_links, audits, workflow_runs), apply this pattern:

```sql
-- Enable RLS
ALTER TABLE public.{table} ENABLE ROW LEVEL SECURITY;

-- SELECT policy
CREATE POLICY "{table}_select_own" ON public.{table}
  FOR SELECT USING (auth.uid() = user_id);

-- INSERT policy
CREATE POLICY "{table}_insert_own" ON public.{table}
  FOR INSERT WITH CHECK (auth.uid() = user_id);

-- UPDATE policy
CREATE POLICY "{table}_update_own" ON public.{table}
  FOR UPDATE USING (auth.uid() = user_id) WITH CHECK (auth.uid() = user_id);

-- DELETE policy
CREATE POLICY "{table}_delete_own" ON public.{table}
  FOR DELETE USING (auth.uid() = user_id);
```

Apply this exact pattern to all 10 tables. Name policies with the table name prefix (e.g., `projects_select_own`, `stages_select_own`, etc.).

No exceptions — every table gets all four policies (SELECT, INSERT, UPDATE, DELETE). The policy logic is identical for all tables because every table has `user_id UUID REFERENCES auth.users(id)`.

Create `lib/supabase/vault.ts` as a server-only module:

```typescript
import 'server-only'
import { createClient } from '@supabase/supabase-js'

// This module MUST only be imported in Server Components, Server Actions, or Route Handlers.
// It will throw at build time if imported in a Client Component.

const supabaseAdmin = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL!,
  process.env.SUPABASE_SERVICE_ROLE_KEY!,
  { auth: { autoRefreshToken: false, persistSession: false } }
)

type SecretName = 'DATAFORSEO_API_KEY' | 'SEMRUSH_API_KEY' | 'OPENAI_API_KEY'

/**
 * Retrieve an API key from Supabase Vault.
 * Must only be called from server-side code (Server Actions, Route Handlers, Edge Functions).
 * Never expose the return value to the client.
 *
 * Keys must be inserted into Vault manually via Supabase Dashboard or CLI:
 *   SELECT vault.create_secret('your-key-value', 'DATAFORSEO_API_KEY');
 */
export async function getVaultSecret(name: SecretName): Promise<string> {
  const { data, error } = await supabaseAdmin
    .from('vault.decrypted_secrets')
    .select('decrypted_secret')
    .eq('name', name)
    .single()

  if (error || !data) {
    throw new Error(`Vault secret '${name}' not found or access denied: ${error?.message}`)
  }

  return data.decrypted_secret
}
```

Add `SUPABASE_SERVICE_ROLE_KEY=your-service-role-key` to `.env.local.example`.

Also add `server-only` to package.json dependencies:
```
npm install server-only
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Supabase client (browser) → Postgres | RLS enforces per-row access control here |
| Server Action / Route Handler → Vault | Service role key used; must stay server-side only |
| .env.local → Next.js process | SUPABASE_SERVICE_ROLE_KEY must NOT be prefixed NEXT_PUBLIC_ |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Elevation of Privilege | RLS bypass via service role | mitibase | Service role key only in `lib/supabase/vault.ts` (server-only); never passed to createBrowserClient; NEXT_PUBLIC_ prefix never applied to service role key |
| T-03-02 | Information Disclosure | SUPABASE_SERVICE_ROLE_KEY in env | mitigate | Key is in .env.local (gitignored), documented in .env.local.example as placeholder; never committed |
| T-03-03 | Information Disclosure | vault.decrypted_secrets view | mitigate | Only accessible via service role key; Vault encrypts at rest using pgsodium; getVaultSecret() is `server-only` import — Next.js build-time guard prevents client import |
| T-03-04 | Tampering | User modifying another user's rows | mitigate | RLS UPDATE policies check both USING (existing row owner) and WITH CHECK (new row owner); user cannot change user_id to take ownership of rows |
| T-03-05 | Information Disclosure | Supabase anon key in browser | accept | Anon key is safe to expose per Supabase architecture: it only grants access subject to RLS policies. Service role key is never NEXT_PUBLIC_. |
</threat_model>
