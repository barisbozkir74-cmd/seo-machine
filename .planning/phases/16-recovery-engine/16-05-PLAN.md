<objective>
Wire D-04 — automatic recovery-task resolution. When the user successfully publishes a page package to WordPress (i.e. `page_packages.wp_published_at` is updated), any open or in_progress recovery_task that points to that page_package automatically transitions to status='resolved'. This is the only path through which a row reaches the resolved state.

Purpose: Close the loop. A user who acts on a recovery task by re-publishing the page should not have to manually mark the task resolved.

Output: Modified `publishToWordPress` action with a non-fatal recovery-resolve hook injected after the DB update succeeds.
</objective>

```typescript
  // ─── Phase 16 D-04: Recovery task auto-resolve ─────────────────────────────
  // After a successful WP publish (wp_published_at updated), mark any open/in_progress
  // recovery_task pointing at this page_packages.id as resolved.
  //
  // NON-FATAL: a failure here is logged and ignored. The publish itself already succeeded
  // in WordPress AND in our DB; the user should not see an error because of a bookkeeping
  // hiccup. Worst case: the recovery row stays open and the user can dismiss it manually.
  //
  // Filter rationale:
  //   .eq('source_id', pkg.id)       — pkg.id IS page_packages.id (polymorphic FK convention)
  //   .eq('source', 'page_package')  — defence: prevents accidental match on imported_page rows
  //                                    that happened to share an id (unlikely, but explicit)
  //   .in('status', ['open', 'in_progress']) — never overwrite resolved/dismissed
  try {
    const { error: recoveryUpdateError } = await supabase
      .from('recovery_tasks')
      .update({
        status: 'resolved',
        updated_at: new Date().toISOString(),
      })
      .eq('source_id', pkg.id)
      .eq('source', 'page_package')
      .in('status', ['open', 'in_progress'])

    if (recoveryUpdateError) {
      // non-fatal — log and continue
      console.warn(
        '[publishToWordPress] recovery auto-resolve failed:',
        recoveryUpdateError.message,
      )
    }
  } catch (e) {
    // non-fatal — log and continue
    console.warn(
      '[publishToWordPress] recovery auto-resolve threw:',
      e instanceof Error ? e.message : String(e),
    )
  }

  revalidatePath(`/projeler/${projectId}/izleme`)
```

**Critical rules:**
1. The added `revalidatePath('/projeler/${projectId}/izleme')` at the end refreshes the izleme page cache so a user navigating from publish → izleme sees the resolved state immediately.
2. DO NOT replace any existing code in publishToWordPress — only INSERT this block. The two existing `revalidatePath` calls (`icerik-studio/${pageId}`, `sayfa-paketi`) MUST be preserved exactly as they are.
3. The `try/catch` is **belt and suspenders**: the Supabase JS client returns errors as `{ error }` (the if-check), but if the underlying network throws, the catch captures it. EITHER path falls through silently — the publish must not fail because of recovery bookkeeping.
4. Use the SAME `supabase` client variable that was already created in publishToWordPress (cookie-bound, line ~475). DO NOT create a new client. RLS UPDATE policy on recovery_tasks (Plan 16-01) gates the update.
5. The filter `eq('source', 'page_package')` is critical — without it, a future hypothetical `imported_page` row whose source_id collided with a page_packages.id (UUID collision is astronomically unlikely but still possible by misconfiguration) could be wrongly resolved.
6. The filter `in('status', ['open', 'in_progress'])` is critical — prevents overwriting `dismissed` status (user explicitly dismissed) or already-`resolved` (idempotent re-publish).
7. The block uses `console.warn` (not `console.error`) because this path is expected to fire on every publish — error severity would generate alarmist log noise. The publish itself is fine.
8. **No project_id filter is needed on the recovery_tasks UPDATE** — `pkg.id` (page_packages.id) is globally unique across projects (UUID PK), so source_id+source uniquely identifies the row. The RLS UPDATE policy (defence-in-depth) confines the update to rows the user can see anyway.
9. **No new imports needed** — `supabase` and `revalidatePath` are already imported at the top of actions.ts.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-05-01 | Tampering | wrong row resolved (cross-tenant) | mitigate | RLS UPDATE policy on recovery_tasks restricts to projects owned by auth.uid(). Defence-in-depth: source='page_package' + source_id=pkg.id is uniquely scoped to the just-published package. |
| T-16-05-02 | Tampering | dismissed row overwritten to resolved | mitigate | `.in('status', ['open', 'in_progress'])` filter excludes 'dismissed' and 'resolved'. |
| T-16-05-03 | Repudiation | silent failure leaves recovery row open | accept | Documented behaviour. Worst case: user manually dismisses. console.warn captures the failure for debugging. The alternative (failing the publish) is unacceptable — publish already succeeded. |
| T-16-05-04 | Information Disclosure | error message leaks DB internals via response | mitigate | The recovery error never appears in the function's return value — only in console.warn. |
| T-16-05-05 | DoS | recovery update slow → publish latency | accept | Indexed UPDATE on (source, source_id, status) — sub-millisecond. Adds at most one round-trip to publish latency. |
| T-16-05-06 | Tampering | service-role key exposed | accept | This action uses the cookie-bound client, NOT service role. SUPABASE_SERVICE_ROLE_KEY is unused here. |
</threat_model>
