**Section 2 — CREATE TABLE (per D-02, D-03):**
```sql
CREATE TABLE IF NOT EXISTS public.recovery_tasks (
  id               UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  project_id       UUID REFERENCES public.projects(id) ON DELETE CASCADE NOT NULL,
  source           TEXT NOT NULL
    CHECK (source IN ('page_package', 'imported_page')),
  source_id        UUID NOT NULL,
  title            TEXT NOT NULL,
  page_url         TEXT NOT NULL,
  position_before  NUMERIC(5,2),
  position_after   NUMERIC(5,2),
  detected_at      TIMESTAMPTZ DEFAULT now() NOT NULL,
  status           TEXT NOT NULL DEFAULT 'open'
    CHECK (status IN ('open', 'in_progress', 'resolved', 'dismissed')),
  created_at       TIMESTAMPTZ DEFAULT now() NOT NULL,
  updated_at       TIMESTAMPTZ DEFAULT now() NOT NULL
);
```

NOTE on `source_id`: it intentionally has NO foreign key constraint because it points to either `page_packages.id` OR `project_imported_pages.id` depending on `source`. Application-level integrity is enforced by the detect route (16-06) and the publish auto-resolve filter (16-05). Document this with an inline comment after the CREATE TABLE: `-- source_id: polymorphic FK — page_packages.id when source='page_package', project_imported_pages.id when source='imported_page'. No DB-level FK to allow either parent.`

**Section 3 — Indexes:**
```sql
CREATE INDEX IF NOT EXISTS idx_recovery_tasks_project
  ON public.recovery_tasks(project_id);
CREATE INDEX IF NOT EXISTS idx_recovery_tasks_project_status
  ON public.recovery_tasks(project_id, status);
CREATE INDEX IF NOT EXISTS idx_recovery_tasks_source_lookup
  ON public.recovery_tasks(source, source_id, status);
```
The third index speeds up duplicate-prevention lookups in the detect route AND auto-resolve UPDATE in publishToWordPress (both filter on source + source_id + status).

**Section 4 — updated_at trigger (copy verbatim from page_packages migration lines 47-50):**

  FOR EACH ROW EXECUTE FUNCTION public.set_updated_at();

**Section 5 — RLS:**
```sql
ALTER TABLE public.recovery_tasks ENABLE ROW LEVEL SECURITY;

CREATE POLICY "recovery_tasks_select_own"
  ON public.recovery_tasks FOR SELECT
  USING (
    EXISTS (
      SELECT 1 FROM public.projects p
      WHERE p.id = recovery_tasks.project_id
        AND p.user_id = auth.uid()
    )
  );

CREATE POLICY "recovery_tasks_update_own"
  ON public.recovery_tasks FOR UPDATE
  USING (
    EXISTS (
      SELECT 1 FROM public.projects p
      WHERE p.id = recovery_tasks.project_id
        AND p.user_id = auth.uid()
    )
  )
  WITH CHECK (
    EXISTS (
      SELECT 1 FROM public.projects p
      WHERE p.id = recovery_tasks.project_id
        AND p.user_id = auth.uid()
    )
  );

-- INSERT/DELETE: service role only (n8n detect route, server-action publishToWordPress auto-resolve).
-- Service role bypasses RLS — no INSERT/DELETE policy declared for end-users.
-- User-initiated mutations (dismiss, in_progress) go through the UPDATE policy via the anon-key
-- server-side client in updateRecoveryTaskStatus (Plan 16-04). Note that updateRecoveryTaskStatus
-- ALSO performs explicit ownership verification before issuing the UPDATE — RLS is defence-in-depth.
```
The UPDATE policy is required because the user-initiated server action `updateRecoveryTaskStatus` (Plan 16-04) uses the cookie-bound `createClient()` (anon key + auth context) — NOT the service role.

**File ordering:** sections must appear strictly in the order: header → CREATE TABLE → indexes → trigger → RLS. No content other than what is specified above.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer machine → Supabase | DDL applied via `supabase db push` (authenticated CLI) |
| end-user (browser) → recovery_tasks SELECT | RLS gate — user can only read tasks for projects they own |
| end-user → recovery_tasks UPDATE (dismiss / in_progress) | RLS gate + server-action ownership re-check (defense-in-depth) |
| n8n service-role → recovery_tasks INSERT | Service role bypasses RLS; webhook secret + ownership check at route level (Plan 16-06) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-01-01 | Tampering | recovery_tasks.status enum | mitigate | DB CHECK constraint restricts to ('open','in_progress','resolved','dismissed') — invalid values rejected at insert/update time |
| T-16-01-02 | Tampering | recovery_tasks.source enum | mitigate | DB CHECK constraint restricts to ('page_package','imported_page') |
| T-16-01-03 | Information Disclosure | cross-tenant SELECT | mitigate | RLS SELECT policy via `EXISTS (… projects p WHERE p.user_id = auth.uid())` — user A cannot read user B's tasks |
| T-16-01-04 | Tampering | cross-tenant UPDATE | mitigate | RLS UPDATE policy USING + WITH CHECK both reference projects.user_id = auth.uid() — prevents user A from mutating user B's tasks even via direct PostgREST |
| T-16-01-05 | Spoofing | source_id without DB-level FK | accept | source_id is polymorphic (page_packages.id OR project_imported_pages.id). No DB FK because PostgreSQL does not support polymorphic FKs without triggers. Application enforces integrity in detect route (16-06) by INSERTing only after verifying parent row exists. Risk: stale source_id after parent deletion. Acceptance: parent tables both have ON DELETE CASCADE on project_id, so deleting a project removes both parents AND recovery_tasks (via project_id CASCADE) atomically. |
| T-16-01-06 | Denial of Service | unbounded recovery_tasks growth | accept | Each detect run inserts ≤ N rows where N = pages with decay. Duplicate-prevention check in detect route (16-06) skips already-open tasks. Per-project growth bounded by total page count. No mitigation needed at MVP scale. |
| T-16-01-07 | Tampering | direct database write bypassing app | mitigate | Service-role key stored in `SUPABASE_SERVICE_ROLE_KEY` env var (server-only — never NEXT_PUBLIC). RLS protects all anon-key paths. |
| T-16-01-08 | Information Disclosure | timing oracle on RLS EXISTS subquery | accept | Standard Supabase RLS pattern; same pattern used in 9 prior migrations. No PII in recovery_tasks (just URLs, position deltas, timestamps). |
</threat_model>
