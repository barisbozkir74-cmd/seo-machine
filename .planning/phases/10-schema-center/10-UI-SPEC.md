### Tab Bar (yeni — PagePackageEditor içinde)

Tab navigation is **client-side state** (`useState<'paket' | 'schema'>`) inside `PagePackageEditor.tsx`. Rationale: the component is already `'use client'`, page selection is state-driven, and adding `searchParams` would require lifting the tab into the server-rendered page — unnecessary complexity for a two-tab local toggle.

```
┌──────────────────────────────────────────────────────────────┐
│  [Paket]  [Schema]                                           │
│  ──────                                                      │
│  (active tab underlined with border-b-2 border-foreground)   │
└──────────────────────────────────────────────────────────────┘
```

Tab bar placement: between the editor header block (badges + action buttons + AI feedback) and the LockedBanner / form content. Tab bar renders only when a `pkg` row exists — before package creation, no tabs are shown (only "AI ile Üret" and "Manuel Başlat" remain visible).

Tab bar markup pattern:
```
<div className="flex gap-1 border-b border-border">
  <button className={cn("px-3 py-2 text-sm ...", activeTab === 'paket' && "border-b-2 border-foreground font-semibold")}>
    Paket
  </button>
  <button className={cn("px-3 py-2 text-sm ...", activeTab === 'schema' && "border-b-2 border-foreground font-semibold")}>
    Schema
  </button>
</div>
```

Default active tab: `'paket'` — existing content is unchanged and front-and-center.

## Interaction Contracts

### Tab Navigation

1. User clicks "Schema" tab
2. `activeTab` state switches to `'schema'`
3. Form section content unmounts; Schema tab content mounts (no scroll reset — tab bar is inline)
4. User clicks "Paket" tab → returns to full scroll form

Tab switching does NOT trigger a save or router.refresh(). It is pure UI state.

### Schema Generation Flow ("Schema Üret")

1. User is on "Schema" tab with no existing schema (empty state)
2. User clicks "Schema Üret" (outline button)
3. Button shows "Üretiliyor..." + disabled (brief — client-side computation is synchronous)
4. `generateSchemaJsonLd(page)` function runs client-side, returns JSON-LD object
5. `schemaJsonLd` state is set with `JSON.stringify(result, null, 2)` — 2-space indented string
6. Schema textarea becomes visible (empty state disappears)
7. Button label returns to "Schema Üret" (idle)

If schema already exists ("Yeniden Üret" variant):
- No overwrite confirmation dialog — generation is cheap and deterministic; user can undo by not saving
- Overwrites `schemaJsonLd` state immediately
- Does NOT auto-save — user must click "Kaydet" to persist

Locked state: "Schema Üret" button is `disabled` when `isLocked === true`. Textarea is also `disabled`.

### Copy Flow ("Kopyala")

1. User clicks "Kopyala" button (ghost, sm)
2. `navigator.clipboard.writeText(schemaJsonLd)` is called
3. Button label immediately changes to "Kopyalandı ✓" in `text-emerald-500`
4. After 2000ms: label reverts to "Kopyala" in default color
5. Error case (clipboard API unavailable): button label shows "Kopyalanamadı" in `text-red-400` for 2000ms, then reverts

Implementation: `useState<'idle' | 'copied' | 'error'>` for copy button state.

### Save Flow (Schema tab)

Same as Phase 9 Paket tab save flow. `handleSave()` sends `schema_jsonld: parseJsonField(schemaJsonLd)` alongside all other fields to `updatePagePackage`. No separate save action for schema.

## Schema Template Spec (generation logic contract)

The `generateSchemaJsonLd(page: PageData)` function runs client-side. Input: `PageData` object. Output: plain JavaScript object (caller stringifies with `JSON.stringify(result, null, 2)`).

### page_type → @type Mapping

| page_type value | JSON-LD @type |
|-----------------|--------------|
| `homepage` | `["Organization", "WebSite"]` (array — dual schema) |
| `category` | `"WebPage"` |
| `service` | `"Service"` |
| `product` | `"Product"` |
| `blog` | `"Article"` |
| `landing` | `"WebPage"` |
| `null` / unknown | `"WebPage"` (fallback) |

FAQPage augmentation: if `faq` field is non-empty JSON array, append a second schema object with `@type: "FAQPage"` to the output array. Output becomes an array of two schema objects wrapped in a `<script>` block.

### Required Fields in Every Schema Object

```json
{
  "@context": "https://schema.org",
  "@type": "...",
  "name": "{seo_title or page.title as fallback}",
  "description": "{meta_description or empty string}",
  "url": "{canonical_url or empty string}"
}
```

### Optional Fields (include when available, omit when null/empty)

| Field | Condition | JSON-LD key |
|-------|-----------|-------------|
| `seo_title` | non-empty | `"name"` |
| `meta_description` | non-empty | `"description"` |
| `canonical_url` | non-empty | `"url"` |
| FAQ items | `faq` array has entries | `"mainEntity"` array on FAQPage object |

Fields NOT included: publisher, logo, datePublished, author — these require project-level data not available in `PageData` and add Phase 11 complexity. Keep Phase 10 output minimal and accurate.

### Output Format

Output is a **single JSON object** (or array of objects if FAQPage augmented), NOT wrapped in `<script>` tags. The user copies raw JSON. This is consistent with D-07 and avoids assumptions about how the user will embed the schema.
