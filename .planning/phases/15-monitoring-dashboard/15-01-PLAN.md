<objective>
Build the data layer for the monitoring dashboard: a single aggregation library that computes cluster-level and page-level GSC metrics for a project + time period, plus thin API routes that expose those aggregations behind auth + ownership guards. Implements MON-01 (cluster summary) and MON-02 (page metrics + decay) data side per D1–D4.

Purpose: Plan 15-02's SSR page imports from this lib directly (no extra HTTP hop), but the API routes also exist so future clients (n8n / external dashboards) can hit them. Centralizing the SQL in one lib avoids duplicating aggregation logic across the SSR page and the routes.

Output: `src/lib/monitoring/aggregation.ts` exporting `getClusterMetrics`, `getPageMetrics`, types `ClusterMetricRow`, `PageMetricRow`, `MonitoringPeriod`; plus two GET API routes under `src/app/api/monitoring/`.
</objective>

    1. Date formatter (replicate pattern from src/app/api/gsc/sync/route.ts:62–64):
       ```typescript
       const fmt = (d: Date) => d.toISOString().split('T')[0]
       const today = new Date()
       const currentStart = new Date(today); currentStart.setDate(today.getDate() - period)
       const priorEnd = new Date(currentStart); priorEnd.setDate(currentStart.getDate() - 1)
       const priorStart = new Date(priorEnd); priorStart.setDate(priorEnd.getDate() - period + 1)
       ```

    2. `getClusterMetrics`:
       - SELECT `gsc_metrics(page_id, clicks, impressions, avg_position)` filtered by `project_id = projectId` and `date >= fmt(currentStart)`.

       - Skip pages whose cluster_id is null.

    3. `getPageMetrics`:

       - SELECT `page_packages(page_id, wp_post_url)` filtered by `project_id = projectId`. Build Map<pageId, wp_post_url>.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → API | Browser/n8n caller sends projectId; route must verify auth + ownership before exposing GSC metrics |
| API → DB | Aggregation library queries gsc_metrics joined to pages — RLS policy `gsc_metrics_select_own` is the last line of defense |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-01-01 | Information Disclosure | /api/monitoring/clusters?projectId={any} | mitigate | Verify auth via `supabase.auth.getUser()` (401 if absent), then SELECT projects WHERE id=projectId AND user_id=user.id (404 if not owned). Identical pattern to gsc/properties route. |
| T-15-01-02 | Information Disclosure | /api/monitoring/pages | mitigate | Same auth + ownership guard as T-15-01-01. Aggregation library uses user-scoped supabase client so RLS enforces `gsc_metrics.project_id` access. |
| T-15-01-03 | Tampering | period query param | accept | Whitelist `7|28|90`; any other value coerces to 28. No SQL injection vector — period is used only as integer in `setDate(d.getDate() - period)`. |
| T-15-01-04 | Denial of Service | Aggregation library scanning entire project history | mitigate | Date filter `date >= currentStart` uses existing index `idx_gsc_metrics_project_date`; period bound to ≤90 days; in-memory reduce is bounded by gsc_metrics rows in window. No unbounded query. |
| T-15-01-05 | Elevation of Privilege | Service-role client bypassing RLS in monitoring routes | mitigate | Acceptance criteria explicitly grep for `createServiceClient|SERVICE_ROLE` returning no matches. Routes use `createClient()` only. |
</threat_model>
